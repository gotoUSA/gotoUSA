# AI가 쓴 코드를 믿지 않고, 재서 고친 기록

Python 외부 API 장애 대응 라이브러리 [Baldur](https://github.com/baldurhq/baldur)를 Claude Code로 혼자 개발했습니다. 코드 대부분은 에이전트가 썼고, 저는 무엇을 잴지, 결과를 믿을지, 출시할지 되돌릴지를 정했습니다.

**요약**: 가짜 서버에서 통과한 기능을 실제 Gemini API로 쟀더니 3~6배 느렸습니다. 원인을 찾아 고쳤지만, 출시 전에 다시 재니 고친 코드가 작업 144개 중 22개를 잃었습니다. 출시하지 않고 되돌렸고, "가짜 서버 통과는 확인이 아니다"를 작업 규칙으로 만들었습니다.

## 작업 절차

AI가 결제사에 없는 서명 방식을 만들어 내고, 같은 가정으로 짠 테스트가 그것을 통과시킨 일을 겪은 뒤 만들었습니다.

- 설계 → 구현 → 테스트 → 검증 단계를 나눈 작업 절차
- 반례만 찾는 읽기 전용 검증 에이전트 — 작성자의 설계와 테스트는 보지 않고 코드만으로 반례를 찾음
- 테스트로 강제하는 아키텍처 규칙 80여 개, 커밋 전 훅, CI

이 장치들은 코드·문서·테스트가 **서로** 맞는지를 봅니다. 실제 환경에서 맞는지는 비어 있었고, 아래가 그걸 알게 된 기록입니다.

## 가짜 서버에서 통과한 숫자를 실제 API로 다시 쟀다

**약속**: 여러 워커가 같은 429(요청 한도 초과)를 맞으면 대기를 하나로 나눠 씁니다. 문서 사이트 첫 화면에는 "요청 8번 → 1번"을 걸어 두었는데, 로컬에서 띄운 가짜 서버(mock 서버)로 낸 숫자였습니다. 표시 없이 거는 건 허위 광고에 가깝다고 보고 실제 API로 먼저 쟀습니다.

**1차 측정**(Gemini 무료 등급, 워커 8개·작업 24개): 실패는 0이었지만 61~85초로, SDK 자체 재시도(13.6~21.6초)보다 3~6배 느렸습니다. 8→1은 재현되지 않았습니다. 원인은 대기가 끝나는 순간 워커를 한꺼번에 풀어 다 같이 다시 거절당한 것(썬더링 허드)이었습니다. 워커를 하나씩 먼저 보내도록 고쳤고, 출시 조건을 "실제 API로 다시 재서 통과"로 정했습니다.

**재측정**(다음 날): 할당량 모양이 달라서, 1분 가까이 한 건도 통과시키지 않았습니다. 고친 코드는 작업 144개 중 22개를 잃었습니다. 원인은 "대기 한 번에 최대 60초"라는 상한이었습니다. 고친 코드에서는 워커가 한 대기 안에 오래 머물러서 60초를 다 써 버렸고, 고치기 전에는 매번 새 대기로 60초를 새로 받았습니다. **상한 값은 그대로인데, 그 뜻이 바뀌어 있었습니다.** 같은 모양의 가짜 서버로 두 버전을 나란히 돌리니 고치기 전 코드는 12회 모두 손실 0, 고친 코드는 12회 중 10회에서 손실이 났습니다.

**결정**: 출시하지 않고 되돌렸습니다. "작업을 잃지 않는다"가 첫 약속이고, 속도는 그다음입니다.

**바꾼 규칙**: 외부 API를 상대로 한 약속은 가짜 서버에서 통과해도 확인으로 치지 않습니다. 공개하는 숫자는 실측에서만 가져오고, 첫 화면의 8→1은 실측한 장애 복구 숫자(12개 멈춤, 12개 복구, 손실 0)로 바꿨습니다.

**범위**: Gemini 무료 등급, 이틀, 할당량 모양 두 가지에서 잰 결과입니다. 할당량이 조금씩 비는 날엔 지금도 SDK 재시도보다 느립니다.

## 같은 패턴의 다른 사례

- 실패한 작업을 디스크에 보관한다는 기능이 구현·테스트·검증을 모두 통과했는데, 보관한 것을 다시 읽어 오는 코드가 없었습니다. 그 뒤 공개 문서에 적힌 약속 314개를 다시 세어 어긋난 15개를 찾았고, 코드를 고치거나 기능을 지우거나 문구를 줄였습니다.
- 출시 뒤 직접 쓰는 앱에 붙이자, 테스트가 잡지 못한 결함 4건(정상 종료 때 보관 기록 유실, 앱의 로거 설정 덮어쓰기 등)이 나왔습니다. 이틀 안에 고쳐 릴리스했습니다.
