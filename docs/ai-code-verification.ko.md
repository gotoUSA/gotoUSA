# AI가 작성한 코드를 실제 환경에서 검증하고 고친 기록

[Django 쇼핑몰 API](https://github.com/gotoUSA/selfhealing)와 Python 외부 API 장애 대응 라이브러리 [Baldur](https://github.com/baldurhq/baldur)를 Claude Code로 혼자 개발했습니다. 코드 대부분은 AI 에이전트로 작성했고, 저는 측정 대상, 결과 채택 여부, 출시와 롤백을 결정했습니다.

이 글은 두 부분으로 나뉩니다.

- **1부. AI가 작성한 코드에서 찾은 결함**: 테스트를 통과한 코드와, 그 테스트를 검사하려고 만든 장치에서 결함을 찾았습니다. 대부분 **코드와 테스트가 같은 잘못된 가정으로 작성되어, 틀린 코드가 테스트를 통과한** 경우였습니다.
- **2부. 지금 AI를 쓰는 방식**: 코드와 테스트가 서로 일치하는지만 보지 않고, 공식 문서와 대조하고, 실제 API에 연결해 보고, 결과를 직접 집계합니다. 각 규칙이 1부의 어느 사례에서 나왔는지도 함께 적었습니다.

**대표 사례**

1. [결제사에 없는 서명을 검사하고 있었다](#1-결제사에-없는-서명을-검사하고-있었다-쇼핑몰): 토스에 없는 서명 방식으로 작성된 코드가 테스트를 통과한 사례
2. [mock 서버에서 통과한 숫자를 실제 API로 다시 측정했다](#3-mock-서버에서-통과한-숫자를-실제-api로-다시-측정했다-baldur): 수정한 코드에서 작업이 유실되는 문제를 출시 전에 찾아 롤백한 사례

사례에서 나온 규칙은 [2부의 규칙 표](#규칙)에 정리했습니다.

# 1부. AI가 작성한 코드에서 찾은 결함

## 1. 결제사에 없는 서명을 검사하고 있었다 (쇼핑몰)

토스페이먼츠 결제 웹훅 수신 코드가 토스에 없는 서명 검증(HMAC 헤더)과 이벤트 이름으로 구현되어 있었습니다. 테스트도 같은 가정으로 작성되어 통과했지만, 실제 토스 웹훅이 왔다면 전부 401로 거부됐을 코드였습니다. 당시 저는 공식 문서와 대조하지 않고 테스트 통과만 보고 넘어갔습니다.

토스 공식 문서의 방식대로 고쳤습니다([`ff741b64`](https://github.com/gotoUSA/selfhealing/commit/ff741b64)). 결제 웹훅에는 서명이 없기 때문에, 지금은 웹훅 본문의 값을 쓰지 않고 트리거로만 사용하며 결제 상태는 결제 조회 API 응답으로 처리합니다. 이후 토스 테스트 환경에서 실제 웹훅을 받아 보니 같은 입금에 웹훅이 두 번 왔고, Redis 중복 필터가 두 번째 요청을 차단한 것을 로그로 확인했습니다.

## 2. DEBUG mock 응답이 틀린 코드를 가렸다 (쇼핑몰)

2025년 12월부터 결제 코드 앞에 `if settings.DEBUG: return {mock 응답}`이 들어가 있어서, 개발 환경에서는 토스 API를 호출하지 않았습니다. 결제 모델의 취소 처리는 처음부터 응답 최상위의 `cancelReason`을 읽고 있었지만, 실제 토스 응답에서 취소 사유는 `cancels[]` 안에 있습니다. mock 응답에도 최상위에 `cancelReason`이 들어 있어서, 실제 환경에서는 취소 사유가 항상 빈 문자열이 되는 코드가 개발 환경에서는 정상으로 동작했습니다.

토스 테스트 환경에 연결해 결함 5개를 찾고 같은 날 고쳤습니다([`b61fea27`](https://github.com/gotoUSA/selfhealing/commit/b61fea27) 등). mock 응답은 실제 토스 응답이 아니라 코드 작성 시점의 가정을 그대로 옮긴 값이었습니다.

## 3. mock 서버에서 통과한 숫자를 실제 API로 다시 측정했다 (Baldur)

**기능**: 여러 워커가 동시에 429를 받으면, 워커마다 따로 백오프하지 않고 공유 대기 하나를 함께 사용합니다. 문서 사이트 첫 화면에 "요청 8번 → 1번"이라는 숫자를 적어 두었는데, 로컬 mock 서버에서 측정한 값이었습니다. 측정 조건을 밝히지 않고 공개하면 과장 광고가 된다고 판단해, 실제 API로 다시 측정했습니다.

**1차 측정**(Gemini 무료 등급, 워커 8개, 작업 24개): 실패는 0건이었지만 61~85초가 걸렸습니다. Gemini SDK 자체 재시도(13.6~21.6초)보다 3~6배 느렸고, 8→1도 재현되지 않았습니다. 원인은 공유 대기가 끝나는 순간 모든 워커가 동시에 재요청해 다시 429를 받는 thundering herd였습니다. 워커를 하나씩 먼저 보내도록 고쳤고, 출시 조건을 "실제 API 재측정 통과"로 정했습니다.

**재측정**(다음 날): 이날은 1분 가까이 모든 요청이 거부됐습니다. 수정한 코드에서는 작업 144개 중 22개가 유실됐습니다. 원인은 "대기 1회 최대 60초"라는 상한이었습니다. 수정 전 코드는 재시도마다 새 대기를 시작해 60초 상한이 매번 새로 적용됐고, 수정한 코드는 워커가 한 대기 안에 계속 머물다가 60초 상한에 도달해 작업이 실패했습니다. **60초라는 값은 그대로였지만, 코드를 고치면서 그 값의 의미가 바뀌어 있었습니다.** 그날 실제 API의 응답 패턴을 재현한 mock 서버로 두 버전을 함께 돌린 결과, 수정 전 코드는 12회 모두 유실 0건, 수정한 코드는 12회 중 10회에서 유실이 발생했습니다.

**결정**: 출시하지 않고 롤백했습니다. 이 라이브러리에서 가장 중요한 요구 사항은 작업 유실이 없는 것이고, 속도는 그다음입니다. 첫 화면의 8→1은 실제로 측정한 장애 복구 결과(멈춘 작업 12개, 복구 12개, 유실 0개)로 바꿨습니다.

**범위**: Gemini 무료 등급에서, 할당량 상태가 서로 다른 이틀 동안 측정한 결과입니다. 요청 한도가 조금씩만 풀리는 날에는 지금도 SDK 재시도보다 느립니다.

## 4. "검증됨" 상태였는데, DLQ에 쓰기만 하고 읽는 코드가 없었다 (Baldur)

끝내 실패한 호출을 디스크에 보관했다가 재실행하는 DLQ 기능이 구현, 테스트, 검증 단계를 통과했지만, 쓰기 코드만 있고 다시 읽어 오는 코드는 없었습니다. 설계 문서는 쓰기만 다뤘고, 코드 주석에는 구현되지 않은 "시작 시 복구"가 설명되어 있었고, 테스트는 쓰기만 검사했습니다. 검증 에이전트도 읽기가 빠진 설계 문서와 코드를 비교했기 때문에 결과가 "일치"로 나왔습니다.

이후 공개 문서에서 기능이 동작한다고 적은 문장 314개를 하나씩 다시 대조해, 실제 코드와 다른 15개를 찾았습니다. 각각 코드를 고치거나, 기능을 삭제하거나, 문서의 과장된 표현을 고쳤습니다.

## 5. "자동으로 검사된다"던 규칙 대부분에 검사가 없었다 (Baldur)

CLAUDE.md에는 "아래 규칙 다수가 자동으로 검사된다"는 문장과 함께 규칙 18개가 적혀 있었습니다. 규칙, 게이트, 스킬을 전수 감사한 결과 실제 게이트가 있는 규칙은 약 7개였습니다. 존재하지 않는 경로를 검사해서 항상 통과하던 테스트도 2개 있었고, 그중 설정 하드코딩 금지 테스트는 경로를 바로잡자 위반 4건이 나왔습니다.

공개 문서의 규칙 목록을 "기계 검사(Mechanically checked)"와 "관례(Conventions)"로 나눴습니다. 항상 통과하던 테스트는 삭제하거나 고쳤고, 검사 대상이 없으면 PASS가 아니라 SKIP으로 표시되게 했습니다.

## 6. 이름만 다르고 기능이 같은 함수가 반복해서 생성됐다 (Baldur)

기존 중복 검사는 이름이 같은 함수만 찾았습니다. 이름은 다르지만 기능이 같은 함수를 찾기 위해 호출 패턴(함수가 내부에서 호출하는 함수)으로 비슷한 함수 묶음을 추출하고, 그중 약 35개를 코드로 직접 확인했습니다. 실제 중복은 20묶음이었고, 그중 9묶음은 이미 서로 다르게 동작하고 있었습니다. 예를 들어 문자열을 불리언으로 파싱하는 코드가 67곳에 따로 있었는데 허용하는 값이 서로 달라서, 같은 `on` 값을 넣어도 설정에 따라 켜지기도 하고 꺼지기도 했습니다.

직접 확인한 세 묶음(락, 쿠버네티스 Lease, 불리언 파싱)은 정본 모듈 목록에 등록하고, 사본 수를 고정하는 게이트를 추가했습니다. 한계도 있습니다. 이 도구의 정밀도는 묶음 기준 약 1/3이라 게이트가 아니라 리포트 용도로만 사용합니다. 사본 수 게이트도 개수만 검사하기 때문에, 사본 하나를 지우고 새로 하나를 만들면 통과합니다.

## 7. 도그푸딩에서 테스트가 놓친 결함이 나왔다 (Baldur)

출시 후 Baldur를 적용한 도그푸딩용 앱을 만들어 실행하자, 테스트에서 잡지 못한 결함 4건이 나왔습니다. 예를 들어 프로세스가 정상 종료될 때 DLQ 버퍼가 flush되지 않았고, 라이브러리가 앱의 로거 설정을 덮어썼습니다. 이틀 안에 고쳐 릴리스했습니다.

# 2부. 지금 AI를 쓰는 방식

## 역할

코드는 AI 에이전트로 작성하고, 저는 측정 대상, 결과 채택 여부, 출시와 롤백을 결정합니다. 그래서 제 작업의 대부분은 결과가 실제로 검증된 것인지 따지는 일입니다.

## 작업 절차

- 설계, 구현, 테스트, 검증 단계를 나눈 작업 절차
- 읽기 전용 검증 에이전트: 구현 단계의 설계 문서와 테스트를 입력에서 빼고, 코드만으로 반례를 찾음
- 테스트로 강제하는 아키텍처 규칙 80여 개와 CI

이 장치들은 코드, 문서, 테스트가 **서로** 일치하는지를 검사하고, 실제 환경에서 동작하는지는 검사하지 못합니다. 1부 사례 대부분이 이 부분에서 나왔고, 아래 규칙은 이를 보완하려고 추가했습니다.

## 규칙

| 규칙 | 관련 사례 |
|---|---|
| 외부 API는 공식 문서와 대조한 뒤, 테스트 환경에 실제로 연결해 응답을 받아 봅니다 | 1부 1, 2 |
| mock 서버나 mock 응답에서 통과한 결과는 검증으로 인정하지 않습니다. 실제 API에서 관찰한 상황을 재현한 mock만 예외입니다. 공개하는 숫자는 실제로 측정한 값만 씁니다 | 1부 3, 표의 mock 관련 행 |
| 모든 작업 보고에 **"실행하지 않은 것"** 항목을 넣습니다. 기능마다 실제로 실행한 부분과 실행하지 않은 부분을 나눠 적고, "검증됨"은 실제로 실행한 것에만 씁니다. 보관과 복구 기능은 코드 리뷰만으로는 검증으로 인정하지 않고, 재시작 후 실제로 다시 읽어 와야 검증된 것으로 봅니다 | 1부 4 |
| 버그를 고칠 때는 재현 테스트를 먼저 작성하고, 그 테스트가 **수정 전 코드에서 실패하는 것**을 확인합니다. 수정 후 그 테스트가 통과해야 수정 완료로 봅니다 | 표의 마지막 행 |
| "자동으로 검사된다"는 문서 내용도 검증합니다. 문서의 규칙 목록은 기계 검사와 관례를 나눠 적고, 검사 대상이 없으면 PASS가 아니라 SKIP으로 표시합니다 | 1부 5 |
| 작업을 시작할 때 "이 기능이 제공하는 것 / **제공하지 않는 것**"을 먼저 정리해 확정합니다. "가장 좋은 방식으로 만들라"고만 지시하면 구현 방식은 정해지지만 기능의 범위는 정해지지 않습니다. Baldur에서도 일반적으로 알려진 장애 대응 기능은 빠짐없이 구현됐지만, 어떤 상황에서 동작하지 않는지는 측정한 뒤에야 알았습니다 | 1부 3, 4 |

## 측정 후 만들지 않기로 한 것

검사를 무조건 늘리지는 않았습니다. 9월 작업 기록을 집계해 보니, 파이썬 파일을 수정한 커밋 129회 중 124회는 커밋 전에 이미 pytest를 실행하고 있었습니다. 그래서 커밋 게이트 훅은 만들지 않았습니다. 서브에이전트 기본 모델을 경량 모델로 바꾸는 것도 검토했지만, 상위 모델을 쓰던 작업 대부분이 전체 검증과 감사처럼 품질이 중요한 작업이어서 측정 후 철회했습니다.

## 아직 해결하지 못한 것

- **규칙이 사람이 모두 읽기 어려울 만큼 많아졌습니다.** 사고가 날 때마다 규칙이 하나씩 늘었습니다. 지금은 새 규칙을 추가할 때 삭제할 규칙을 함께 적도록 했지만, 이미 쌓인 규칙은 그대로입니다.
- **검사 장치는 코드 사이의 불일치는 잡지만, 실제 환경에서 동작하는지는 잡지 못합니다.** 실제 환경 측정은 지금도 제가 직접 지시해야 이뤄집니다(1부 1, 2, 3).
