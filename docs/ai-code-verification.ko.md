# AI가 쓴 코드를 믿지 않고, 재서 고친 기록

[Django 쇼핑몰 API](https://github.com/gotoUSA/selfhealing)와 Python 외부 API 장애 대응 라이브러리 [Baldur](https://github.com/baldurhq/baldur)를 Claude Code로 혼자 개발했습니다. 코드 대부분은 AI 에이전트가 썼고, 저는 무엇을 잴지, 결과를 믿을지, 출시할지 되돌릴지를 정했습니다.

이 글은 두 부분입니다.

- **1부. AI가 쓴 코드에서 찾은 것**: 테스트를 통과한 코드에서, 그리고 그 테스트를 걸러 내려고 만든 검사 장치에서도 틀린 것을 찾았습니다. 공통점은 **AI가 틀린 가정으로 코드를 짜고, 테스트도 같은 가정으로 짜서, 틀린 코드가 테스트를 통과했다**는 것입니다.
- **2부. 그래서 AI를 이렇게 씁니다**: 코드와 테스트끼리 맞춰 보는 것으로 끝내지 않고, 그 바깥에 있는 것과 대 봅니다. 공식 문서와 대조하고, 실제 API에 붙여 보고, 결과를 직접 셉니다. 각 규칙이 1부의 어느 사례에서 나왔는지도 같이 적었습니다.

**대표 사례**

1. [결제사에 없는 서명을 검사하고 있었다](#1-결제사에-없는-서명을-검사하고-있었다-쇼핑몰) — AI가 지어낸 서명 방식을 테스트가 통과시킨 사례
2. [mock 서버에서 통과한 숫자를 실제 API로 다시 쟀다](#3-mock-서버에서-통과한-숫자를-실제-api로-다시-쟀다-baldur) — 고친 코드가 작업을 잃는 걸 출시 전에 찾아 되돌린 사례

이 사례들에서 나온 규칙은 [2부의 규칙 표](#규칙)에 모아 두었습니다.

# 1부. AI가 쓴 코드에서 찾은 것

## 1. 결제사에 없는 서명을 검사하고 있었다 (쇼핑몰)

토스페이먼츠 결제 웹훅 수신 코드가 AI가 지어낸 서명 검증(HMAC 헤더)과 이벤트 이름을 구현하고 있었습니다. 둘 다 토스에는 없는 것이었습니다. 테스트도 같은 가정으로 짜여 있어 통과했고, 실제 토스 웹훅이 왔다면 전부 401로 거부됐을 코드였습니다. 저는 그때 공식 문서와 대조하지 않고 테스트 통과를 확인으로 여겼습니다.

토스 공식 문서에 적힌 방식대로 고쳤습니다([`ff741b64`](https://github.com/gotoUSA/selfhealing/commit/ff741b64)). 결제 웹훅에는 서명이 없습니다. 그래서 지금은 웹훅 본문을 믿지 않고 트리거로만 쓰고, 결제 조회 API 응답으로 상태를 처리합니다. 그다음 토스 테스트 환경에 붙여 실제 웹훅을 받아 봤습니다. 같은 입금에 웹훅이 두 번 왔고, 중복 필터(Redis)가 두 번째를 막는 것을 로그로 확인했습니다.

## 2. DEBUG mock 응답이 틀린 코드를 가렸다 (쇼핑몰)

2025년 12월부터 결제 코드 앞에 `if settings.DEBUG: return {mock 응답}`이 들어가 있어서, 개발 환경은 토스를 아예 호출하지 않았습니다. 그런데 결제 모델의 취소 처리는 처음부터 응답 최상위의 `cancelReason`을 읽고 있었고, 실제 토스는 취소 사유를 `cancels[]` 안에 넣어 보냅니다. mock 응답도 최상위에 `cancelReason`을 넣어 두어서, 실제로는 취소 사유가 늘 빈 문자열이 되는 코드가 개발 환경에서는 정상으로 보였습니다.

토스 테스트 환경에 붙여 결함 5개를 찾고 같은 날 고쳤습니다([`b61fea27`](https://github.com/gotoUSA/selfhealing/commit/b61fea27) 등). mock 응답에는 실제 토스의 응답이 아니라, mock을 만든 쪽이 "이렇게 답하겠지" 하고 생각한 것이 들어 있었습니다.

## 3. mock 서버에서 통과한 숫자를 실제 API로 다시 쟀다 (Baldur)

**기능**: 여러 워커가 동시에 429를 받으면, 각자 백오프하는 대신 공유 대기 하나를 같이 씁니다. 문서 사이트 첫 화면에는 "요청 8번 → 1번"이라는 숫자를 걸어 두었는데, 로컬 mock 서버를 상대로 낸 숫자였습니다. 그렇다는 표시 없이 거는 건 허위 광고에 가깝다고 보고, 실제 API로 먼저 쟀습니다.

**1차 측정**(Gemini 무료 등급, 워커 8개·작업 24개): 실패는 0이었지만 61~85초가 걸렸습니다. Gemini SDK 자체 재시도(13.6~21.6초)보다 3~6배 느렸고, 8→1도 재현되지 않았습니다. 원인은 공유 대기가 끝나는 순간 워커를 한꺼번에 풀어, 다 같이 재요청했다가 다 같이 다시 429를 받은 것(thundering herd)이었습니다. 워커를 하나씩 먼저 보내도록 고쳤고, 출시 조건을 "실제 API로 다시 재서 통과"로 정했습니다.

**재측정**(다음 날): 이날은 API가 1분 가까이 요청을 한 건도 받아 주지 않았습니다. 고친 코드는 작업 144개 중 22개를 잃었습니다. 원인은 "한 번 기다릴 때 최대 60초"라는 상한이었습니다. 고치기 전 코드는 재시도마다 새 대기를 시작해 60초를 매번 새로 받았고, 고친 코드는 워커가 한 대기 안에 계속 머물러 60초를 다 쓰고 작업을 포기했습니다. **60초라는 숫자는 그대로인데, 코드를 고치면서 그 숫자가 실제로 하는 일이 바뀌어 있었습니다.** 그날 실제 API의 응답 패턴을 따라 만든 mock 서버로 두 버전을 나란히 돌리니, 고치기 전 코드는 12회 모두 잃은 작업 0개, 고친 코드는 12회 중 10회에서 작업을 잃었습니다.

**결정**: 출시하지 않고 되돌렸습니다. "작업을 잃지 않는다"가 이 라이브러리의 첫 약속이고, 속도는 그다음입니다. 첫 화면의 8→1은 실제로 잰 장애 복구 숫자(멈춘 작업 12개, 복구 12개, 잃은 것 0개)로 바꿨습니다.

**범위**: Gemini 무료 등급에서, 이틀 동안, 할당량 상태가 서로 다른 두 날에 잰 결과입니다. 요청 한도가 조금씩만 풀리는 날에는 지금도 SDK 재시도보다 느립니다.

## 4. "검증됨"이었는데, DLQ에 쓰기만 하고 읽는 코드가 없었다 (Baldur)

끝내 실패한 호출을 디스크에 보관했다가 재실행하는 DLQ 기능이 구현·테스트·검증 단계를 모두 통과했는데, 쓰기만 있고 다시 읽어 오는 코드는 없었습니다. 설계 문서는 쓰기만 다뤘고, 코드 주석은 있지도 않은 "시작할 때 복구"를 설명했고, 테스트는 쓰기만 확인했고, 검증 에이전트는 똑같이 읽기가 빠진 설계 문서와 코드를 비교해서 일치한다고 판단했습니다.

그 뒤 공개 문서가 "된다"고 적어 둔 문장 314개를 하나씩 다시 확인해서, 실제 코드와 다른 15개를 찾았습니다. 코드를 고치거나, 기능을 지우거나, 문서에서 과장된 말을 뺐습니다.

## 5. "자동으로 검사된다"던 규칙 대부분에 검사가 없었다 (Baldur)

CLAUDE.md에는 "아래 규칙 다수가 자동으로 검사된다"는 문장과 함께 규칙 18개가 적혀 있었습니다. 규칙·게이트·스킬을 전수 감사해 보니, 실제 게이트가 있는 건 약 7개였습니다. 없는 경로를 검사해서 항상 통과하던 테스트도 2개 있었습니다. 그중 하나는 설정 하드코딩 금지 테스트였는데, 경로를 바로잡자마자 위반 4건이 나왔습니다.

공개 문서의 규칙 목록을 "기계 검사(Mechanically checked)"와 "관례(Conventions)" 두 목록으로 나눴습니다. 항상 통과하던 테스트는 지우거나 고쳤고, 검사할 대상이 없으면 PASS가 아니라 SKIP으로 보이게 했습니다.

## 6. AI는 같은 기능의 함수를 이름만 바꿔 또 만든다 (Baldur)

"검사가 이름이 같은 함수만 찾는 거 아니냐, 이름은 다른데 하는 일이 같은 함수는?"이라는 의문에서 시작했습니다. 호출 패턴(함수가 무엇을 부르는지)으로 비슷한 함수 묶음을 찾고, 그중 약 35개를 코드로 직접 확인했습니다. 진짜 중복은 20묶음이었고, 그중 9묶음은 이미 서로 다르게 동작하고 있었습니다. 예를 들어 문자열을 불리언으로 파싱하는 코드가 67곳에 따로 있었는데 허용하는 값이 제각각이라, 똑같이 `on`이라고 써도 어떤 설정은 켜지고 어떤 설정은 꺼졌습니다.

직접 확인한 묶음 셋(락, 쿠버네티스 Lease, 불리언 파싱)은 정본 모듈 목록에 올리고, 사본 수를 고정하는 게이트를 넣었습니다. 한계도 있습니다. 이 도구의 정밀도는 묶음 기준 약 1/3이라 게이트가 아니라 리포트용으로만 씁니다. 사본 수 게이트도 개수만 보기 때문에, 하나를 지우고 하나를 새로 만들면 통과합니다.

## 7. 직접 쓰는 앱에 붙이자 테스트가 못 잡은 결함이 나왔다 (Baldur)

출시 뒤 제가 직접 쓰는 앱에 붙이자, 테스트가 잡지 못한 결함 4건이 나왔습니다. 예를 들어 프로세스가 정상 종료할 때 DLQ 버퍼가 flush되지 않았고, 라이브러리가 앱의 로거 설정을 덮어썼습니다. 이틀 안에 고쳐 릴리스했습니다.

# 2부. 그래서 AI를 이렇게 씁니다

## 역할

코드는 AI 에이전트가 쓰고, 저는 무엇을 잴지, 결과를 믿을지, 출시할지 되돌릴지를 정합니다. 그래서 제 일의 대부분은 "이게 정말 확인된 건가"를 묻는 것입니다.

## 작업 절차

- 설계 → 구현 → 테스트 → 검증 단계를 나눈 작업 절차
- 반례만 찾는 읽기 전용 검증 에이전트: 작성 쪽의 설계 문서와 테스트는 보지 않고 코드만으로 반례를 찾음
- 테스트로 강제하는 아키텍처 규칙 80여 개, CI

이 장치들은 코드·문서·테스트가 **서로** 맞는지를 봅니다. 실제 환경에서도 맞는지는 보지 못합니다. 1부 사례 대부분이 그 빈자리에서 나왔고, 아래 규칙은 그 빈자리를 메우려고 생겼습니다.

## 규칙

| 규칙 | 나온 곳 |
|---|---|
| 외부 API는 공식 문서와 대조하고, 거기서 끝내지 않고 테스트 환경에 실제로 붙여 응답을 받아 봅니다 | 1부 1·2 |
| mock 서버·mock 응답에서 통과한 것은 확인으로 치지 않습니다. 실제 API에서 직접 본 상황을 그대로 따라 만든 mock일 때만 확인으로 칩니다. 공개하는 숫자는 실제로 잰 것만 씁니다 | 1부 3, 표의 mock 행들 |
| 모든 작업 보고에 **"돌려 보지 않은 것"** 칸을 둡니다. 기능마다 실제로 돌려 본 부분과 안 돌려 본 부분을 나눠 적고, "검증됨"은 실제로 돌려 본 것에만 씁니다. 보관·복구 기능은 코드를 읽은 것만으로는 확인으로 치지 않고, 재시작한 뒤 실제로 다시 읽어 봐야 확인으로 칩니다 | 1부 4 |
| 버그를 고칠 때는 그 버그를 재현하는 테스트부터 만들고, 그 테스트가 **고치기 전 코드에서 실패하는 것**을 먼저 봅니다. 고친 뒤 그 테스트가 통과해야 고친 것으로 칩니다 | 표의 마지막 행 |
| "검사된다"는 말도 확인합니다. 문서의 규칙 목록은 기계 검사와 관례를 나눠 적고, 검사할 대상이 없으면 PASS가 아니라 SKIP으로 보이게 합니다 | 1부 5 |
| 작업을 시작할 때 "이 기능이 해 주는 것 / **해 주지 않는 것**"을 쉬운 말로 먼저 확인받습니다. "가장 좋은 방식으로 만들라"고만 맡기면 '어떻게 만들지'는 정해져도 '어디까지 책임질지'는 정해지지 않습니다. 실제로 에이전트는 교과서에 나오는 기능을 빠짐없이 넣었고, 어디까지는 안 되는지는 측정하고 나서야 알았습니다 | 1부 3·4 |

## 재 보고 나서 만들지 않기로 한 것

검사를 무조건 늘리지는 않았습니다. 9월 작업 기록으로 세어 보니, 파이썬 파일을 고친 커밋 129회 중 124회는 커밋하기 전에 이미 pytest를 돌리고 있었습니다. 그래서 커밋 게이트 훅은 만들지 않았습니다. 서브에이전트 기본 모델을 경량 모델로 바꾸는 것도 검토했지만, 무거운 모델이 쓰이던 자리가 대부분 전체 검증·감사처럼 품질이 중요한 일이어서 측정한 뒤 철회했습니다.
